# v0.6.1 성능 구조와 검증

## 대량 작업의 복사 후처리

`workspace_index.py`는 새로고침 시 원본 경로의 정규화 결과와 행 위치를 저장한다.
완료 개수는 새로 완료된 파일만 증가시키며 재복사 시 중복 증가하지 않는다.
다음 파일 탐색은 캐시된 경로의 메모리 집합 확인으로 처리하며 파일별 `resolve()`를 호출하지 않는다.
출력 목록은 새 파일과 충돌로 이름이 바뀐 행만 갱신하고 전체 탐색은 폴더 선택/새로고침 때 수행한다.
번호 충돌 검사는 실제 디렉토리를 새로 열되 이름이 일치하는 후보만 파일 여부를 검사한다.

복사 후 다음 선택까지의 중간 상태 저장은 보류하고 최종 상태를 한 번 저장한다.
JSON 형식은 기존과 같으며, 같은 폴더의 임시 파일을 닫은 뒤 `os.replace()`로 교체한다.
상태 구성 시 부모 폴더 확인도 부모 경로별 한 번만 수행한다.
후처리 중에는 목록만 프로그램에서 수정할 수 있게 풀고 진행 막대와 사용자 입력 제한을 유지한다.

### 재현 실험

Mac arm64, 시스템 Python 3.9, 각 5회 중앙값. 파일시스템 연산은 실제 실행하고
화면 그리기, 파일 복사 I/O와 PDF/OCR은 제외했다. 아래 명령으로 비교할 수 있다.

```sh
python tools/benchmark_copy_completion.py --baseline-ref b4a9a6a
```

| 조건 | v0.6.0 후처리 | v0.6.1 후처리 | resolve 호출 전 → 후 |
| --- | ---: | ---: | ---: |
| 700개, 첫 파일 완료 | 13.583ms | 0.476ms | 725 → 3 |
| 1,300개, 1,000개 완료 | 264.528ms | 2.651ms | 14,312 → 3 |

실제 Windows에서의 전체 작업 시간이나 동일 배수의 개선을 보장하는 수치는 아니다.
`test_copy_scaling.py`는 1,300개/1,000개 완료 조건의 상태 저장 1회, 마지막 선택 복원,
중복 경로 확인 제거, 출력 번호 변경 및 상태 파일 교체 실패를 검사한다.

## PDF 처리 구조

Tk 메인 스레드는 화면 표시, 선택, 문서 메타데이터와 좌표 처리, 주소 검색을 담당한다.
PyMuPDF 렌더링은 `pdf_pipeline.py`의 독립된 spawn 프로세스에서 실행한다.
다음 미처리 파일 1개의 텍스트 추출/OCR은 두 번째 프로세스에서 실행한다.
두 프로세스는 작업 완료 후 재사용하며 PDF 객체는 프로세스 사이에서 공유하지 않는다.
파일 복사는 기존 단일 스레드에서 순차 처리한다.

현재 파일의 OCR이 새로 필요하면 다른 파일의 사전 인식을 중단하고 기존 `OcrJob`을 사용한다.
이미 준비 중인 동일 파일·페이지·영역의 작업은 `PreparedOcrJob`으로 전환해 기다린다.
준비된 OCR 결과는 `F8`으로 강제로 새로 인식할 수 있다. 모델은 기존 `tessdata_best`를 유지한다.
워커 재사용은 Python 프로세스 시작 비용을 줄인다. OCR 엔진 내부 모델 재사용을 보장하지 않는다.

현재 렌더링 요청은 키와 문서 열기 세대 번호로 식별한다. 키에는 정규화된 경로,
수정 시각(ns), 파일 크기, 페이지, 표시 배율/뷰어 폭이 들어간다.
주소 영역 캐시 키에는 페이지와 상대 좌표가 들어간다. 종료되거나 교체된 요청의 결과는
현재 화면에 적용하지 않는다. 렌더링 대기 중 주소를 수정하면 예약된 자동 추출을 적용하지 않는다.

실행 중인 이전 렌더링은 요청 교체 시 프로세스를 종료하고 최신 요청으로 대체한다.
크기 변경은 120ms 동안 합치며, 사전 준비는 현재 화면 준비 후 150ms에 시작한다.
활성 작업은 슬롯당 1개로 제한해 큐가 쌓이지 않도록 한다.
이미지 캐시는 64MiB/8건 LRU, 영역 캐시는 1MiB/16건 LRU이다.
픽셀 버퍼와 Tk 이미지, 워커 메모리는 캐시 상한과 별도로 사용한다.

## 진단과 자동 검사

`--performance-report performance.json`으로 GUI를 실행하고 종료하면 숫자 지표만 기록한다.
`file_to_display`는 파일 열기부터 표시 완료까지, `render_worker`는 워커 내부 렌더링 벽시계 시간,
`search`는 검색, `text_extract`는 영역 텍스트 추출, `ocr_wait`는 OCR 요청부터 결과 처리까지,
`ocr_worker`는 OCR 작업 자체의 벽시계 시간을 뜻한다.
`source_refresh`는 원본 목록 재구성, `copy_wait`는 복사 제출부터 결과 처리 시작까지의 시간이다.
v0.6.1의 `copy_precheck`는 입력 검사와 충돌 계획 생성(확인 대화상자 대기 제외),
`state_save`는 상태 구성과 저장, `completion_display`는 완료 행·개수 갱신,
`output_update`는 출력 목록 증분 갱신, `next_selection`은 다음 선택과 열기 요청까지의 시간이다.
`copy_postprocess`는 파일 복사 후 관리 작업, `copy_transaction`은 복사 제출부터
후처리 완료까지이며 비동기 PDF/OCR 대기는 별도의 표시·OCR 지표로 확인한다.
각 구간은 최근 최대 128건의 표본 수·중앙값·최댓값으로 출력한다.

`test_pdf_pipeline.py`는 실제 PDF의 렌더링·텍스트 추출·스캔 OCR과 워커 수명주기를 검사한다.
`test_async_viewer.py`는 이전 세대/확대 요청, 파일 교체, 직접 입력 보존, 크기 변경 합치기,
사전 준비가 파일 선택을 바꾸지 않는지와 기존 검색 결과의 동등성을 검사한다.
GitHub Actions는 빌드한 exe의 `--pipeline-check`를 통해 Windows spawn과 OCR 모델 포함 여부도 검사한다.
